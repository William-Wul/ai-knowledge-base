## 优先建议

### 1. 改善自动更新可靠性

- 日报设置为每天 10:30，但 10/31、11/01、11/02 的定时任务实际分别在 16:39、17:30、17:46 启动。今天截至 16:20，尚无当天日报任务记录，线上落后上游一天；结合近日时间分布，应先判断为更新延迟，继续观察当天任务结果。
- 日报兜底也使用 GitHub 定时任务；目前只检查仓库是否存在当天文件，没有检查线上是否发布成功。主任务和兜底共用同一调度平台，无法保证上午出刊。
- 榜单 10/28—10/31 连续失败，11/01、11/02 恢复。10/30 与 10/31 日志均提示“价格字段异常#6”；保留旧数据的保护有效，10/31 巡检也实际报出超过 48 小时未同步。错误字段的具体上游原值尚未从历史页面还原，不应直接放宽价格校验。
- 建议：明确可接受的更新时间；增加失败后的有限重试和人工处理提醒；补采导致失败的真实样本并针对性兼容；让兜底核对上游、仓库和线上页面是否一致。如必须上午准时更新，再评估独立调度来源。
- 验收：新日报在约定时间前真实上线；模拟抓取失败保留旧数据并产生可见提醒；仓库已有文件而网站未更新时也能发现。

证据：[11/02 日报任务](https://github.com/William-Wul/ai-knowledge-base/actions/runs/41423370593)、[10/31 榜单失败](https://github.com/William-Wul/ai-knowledge-base/actions/runs/41189107972)、[10/31 巡检失败](https://github.com/William-Wul/ai-knowledge-base/actions/runs/41216979818)、[最近榜单恢复](https://github.com/William-Wul/ai-knowledge-base/actions/runs/41432671685)。

### 2. 恢复面向普通员工的人工更新

- 首页“最新前沿观察”仍是 10/13 的 REA 文章，距检查日 21 天；10/27 更新日志是运行修复，最近新增人工内容记录为 10/13。
- 当前首页日报条目包括 OpenRouter 的 Responses API 代码审查脚本、Claude Code 的 ultrathink 技巧，技术门槛较高。该判断来自当日页面抽查，不代表对全部日报的分类统计。
- 建议：先试一周人工精选，从现有资讯中挑 3 件与工作相关的事，每件写清发生什么、影响谁、怎么试、限制与来源；沿用现有文章/栏目组织，不预设新功能。
- 验收：非技术员工读完能说清一项影响，并能照着完成一个具体动作。

### 3. 优先复核常用教程与旧评测

- Codex 教程已有并入 ChatGPT 桌面应用的说明，不能仅凭旧截图判定整篇过时。当前官方资料同样说明在桌面应用内选择 ChatGPT 或 Codex，ChatGPT 内再切换 Chat / Work。
- 需要精确修订的是把 Chat / Work / Codex 简化为“嘴替 / 长工 / 手替”、仿佛只有 Codex 能动手的表述。官方明确 Work 和 Codex 能力有重叠，Work 也能处理文件、运行代码和跨应用任务。界面选择应围绕任务和技术细节偏好讲清楚。
- Claude Code 教程仍写“官方最强 Fable 5”“国内最便宜”“充 10 块钱能跑很久”等比较性结论，应单独核对当前官方型号、套餐与实际任务成本后再保留。本轮未逐条核实这些产品事实，列为待复核项。
- PPT 工具文章已诚实标注为 2026 年 4 月试用、10/09 仅复核口径，不能称为伪装实时评测；但作为常用上手入口，应选目前员工可用的工具重新跑同一份文稿，补可编辑文件、内容保留情况、导出限制、实际成本。
- 建议每轮只复核 2—3 篇高频教程；注明复核日期、复核范围和实际验证的平台。

官方核对：[桌面应用入口](https://learn.chatgpt.com/docs/app)、[Chat / Work / Codex 的选择与能力重叠](https://learn.chatgpt.com/docs/use-chatgpt)。

### 4. 把已有案例做成可复现的练习

- 案例库已达 599 例，分类、关键词搜索和手机列表抽查正常。规模足以支持精选，下一步价值更可能来自实际复现质量。
- 建议先选 5 个现有案例，亲自跑通并补齐可使用的示例材料、可替换位置、完整操作、实际耗时与费用、成品、常见失败及验收办法。由 William 选定优先主题，暂不预设新增课程或进度功能。
- 验收：目标读者能独立做出可检查的结果；未实测案例继续保留准确标记，不把原作者作品写成本站已验证。

### 5. 用现有统计决定后续投入

- 已有百度统计和案例复制、案例下载点击、测评完成等固定动作埋点。
- 建议先看近 30 天访问、常用文章、案例动作和测评完成数量，再选精编文章与案例。本轮未登录百度统计，无法判断实际活跃人数、学习效果或节省工时。
- 点击复制、下载或完成测评只能说明发生了相应动作，不证明学会或产出合格；必要时用少量真实读者试做补充判断。

## 次要维护项

- 构建仍提示存在超过 500 kB 的代码包。本轮没有真实用户加载指标，不宜仅凭警告启动框架升级；先测主要页面首屏和较慢网络，再决定拆分范围。
- 项目手册仍有“四大板块”、4 篇进阶实践、已删除 coding 特色专区等旧描述；实际已有案例、视频课等入口，进阶实践清单也已扩充。后续维护时可同步手册，减少判断新内容归属时的歧义。

## 建议执行顺序

1. 先确定自动更新的时效目标，拟定小范围修复方案；涉及 GitHub Actions 修改须按项目规则另行确认。
2. 内容优先：复核常用教程 + 5 个已有案例实测，方向和范围确认后实施。
3. 人工精选资讯试一周，再用阅读与试用反馈决定是否长期维持。
