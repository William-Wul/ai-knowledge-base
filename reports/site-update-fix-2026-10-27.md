## 需求与验收标准

需求：修复网站已有的日报发布及模型榜单同步故障，并降低同类问题再次长期无人发现的可能。

用户故事：读者打开首页、日报或榜单时，应能看到最新可用数据；维护者需要知道内容是否真正上线，而不仅是抓取任务是否成功。

验收标准：正式构建恢复、当前原榜可正常同步、失败保护不退化、能发现“仓库已更新但线上未更新”，发布后核对线上正文。

## 防止再次发生：推荐实施方案

### 已完成：固定样本、严格校验、上线验收入口

- 固定的新闻和榜单样本归 `tests/fixtures/`，自动同步不会写入此目录。
- 真实日报仍被检查，不因为内容有变化就跳过全部测试。
- 已知名称调整可兼容，未知结构继续失败并保留旧数据，避免为追求“绿色成功”而把错误数据发布出去。
- 发布验收顺序改为“完整构建通过 → 部署成功 → `npm run check:online` 通过”。当前脚本只读检查，尚未部署的新功能缺少快照时会明确失败。

### 已确认：新增一个自动巡检任务

已审阅的完整配置在 [site-health-workflow.yml.example](site-health-workflow.yml.example)。William 已确认，正式配置新增为 `.github/workflows/site-health.yml`，随本次发布生效。现有日报、榜单及部署工作流没有改动。

- 每天北京时间 **12:47、18:47** 各执行一次，也支持手动执行；时刻代表计划时间，不是准点承诺。
- 只读仓库和公开数据，无需新增密钥或安装依赖，不写回仓库，不触发无限补跑。
- 检查两条链路：上游日报是否上线；榜单是否持续同步且线上正文与仓库一致。
- 异常时任务失败，并在任务摘要显示原因。GitHub 是否向你发送通知取决于账号通知偏好，不在本次未经确认地更改，也不保证通知一定送达。
- 保留原有日报漏跑补触发任务；新增巡检补上它无法发现“文件有了但没有上线”的遗漏。

GitHub 官方说明定时任务在高负载时可能延迟甚至丢失，避开整点只能降低概率。因此当前推荐先沿用现有平台、增加明确的结果巡检；若未来要求每天上午准点更新，再单独评估独立调度和独立通知。不能仅修改 cron 就承诺解决已观察到的延迟。来源：[GitHub schedule 说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

### 后续维护约定

- 每次发现来源改版：保存一份当时的页面样本，先验证字段含义，再增加有限的兼容规则。
- 不通过删除测试、忽略同步错误、刷新旧数据时间来伪造成功。
- 线上异常先分辨“来源没有更新、抓取失败、仓库没写入、部署失败、缓存仍旧”发生在哪一步，再决定是否补跑。
- 自动巡检只有失败信号，不自动修改代码。解析逻辑失败需要修复，反复补跑同一个错误没有帮助。
